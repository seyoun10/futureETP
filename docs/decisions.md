## D-004: 기준값 3종과 지수 산출 방식
- 날짜: 2026-10-22 (소급 기록)
- 상태: 확정
- 결정:
  - 대표월물은 전일 거래량 기준으로 정하고, 이전 월물로 되돌아가지 않는다. 최종 거래일에 도달하면 강제로 전환한다.
  - 한국형·미국형은 시장별로 상품 수 기준 다수 규칙을 쓴다. 동률이면 AUM이 큰 쪽을 쓴다.
  - 종가는 정산가를 쓴다. 지수는 세 기준값 모두 수익률 연결 지수(S&P GSCI 방식)로 만들고, 가격 수준 맞춤(back-adjusted)을 적용한다.
  - 혼합 가격이 0 이하인 날은 산출하지 않고, 다음 유효일은 직전 유효일 혼합 가격으로 이어 붙인다(2026-10-22 추가).
  - 해당 기준값의 상품이 없는 원자재는 대표월물로 대신 표시하고 안내한다.
- 근거:
  - 되돌아가지 않는 규칙은 거래량이 엎치락뒤치락할 때 반복 전환을 막는다.
  - 수익률 연결은 ETP NAV처럼 롤 시점의 가격 점프가 없다. 가격 수준 맞춤은 월물 원가격과 같은 단위로 보게 한다.

## D-005: 이격도와 rare 레벨
- 날짜: 2026-10-22 (소급 기록)
- 상태: 확정
- 결정:
  - 이격도는 종가 SMA 기준이다. 이평선은 20/50/100/200일(기본 100), 분포 기간 N은 3/5/10년/전체(기본 10년)다.
  - rare 레벨은 0.1~49.9 범위의 서로 다른 5개 값을 자유 입력한다(기본 5/10/15/20/25).
  - rare-level 선은 현재 분포의 레벨 이격도를 고정해 `이평선 × (1 + 레벨/100)` 밴드로 그린다.
  - 서버는 48개 시계열과 192개 정렬 분포를 미리 계산한다.
- 근거: 정렬 분포가 있으면 자유 입력 백분위도 바로 구할 수 있다. 50은 위·아래 선이 겹쳐 의미가 없다.

- 날짜: 2026-10-23
- 상태: 확정
- 맥락: TODO 2단계. 저장소에 앱(Expo)·서버(Node)·공유 패키지가 있다(D-035). 지수·이평선·분포·롤 비중 같은 핵심 계산은 서버·공유 패키지에 있고, 앱은 화면 코드가 대부분이다. 전역 지침은 작은 단위 작업 → 테스트 → 커밋이다. CLAUDE.md는 default export를 금지하고 `app/` route 파일만 예외로 둔다(D-029).
- 선택지: lint/format은 ESLint + Prettier / Biome. 테스트는 앱 jest-expo + 서버·공유 Vitest / 전부 Jest. 커밋 hook은 lint·format만 / 전부 / 없음
- 결정:
  - lint: ESLint flat config. 앱은 `eslint-config-expo`(`npx expo lint`) 기반이고, 앱·서버 공통으로 `typescript-eslint` 타입 기반 규칙(`no-floating-promises` 등)과 `import/no-default-export`(`app/**` 예외)를 건다.
  - format: Prettier. ESLint와 서식 규칙이 겹치지 않게 한다.
  - 테스트: 앱은 `jest-expo` + React Native Testing Library, 서버·공유 패키지는 Vitest. 핵심 계산은 공유·서버 쪽 단위 테스트로 검증한다.
  - Git hook: husky + lint-staged로 pre-commit에서 바뀐 파일만 `eslint --fix`·`prettier --write`. 타입 검사·lint 전체·테스트는 루트 `npm run check` 한 줄로 묶어 커밋 전에 실행한다.
  - 2026-10-23 npm 기준 최신: `eslint` 10.13.0, `eslint-config-expo` 58.0.4, `typescript-eslint` 8.72.0, `prettier` 3.9.10, `jest-expo` 58.0.12(jest 30), `@testing-library/react-native` 14.1.0, `vitest` 5.0.5, `husky` 9.1.7, `lint-staged` 17.6.0. 실제 버전은 스캐폴딩 때 `npx expo install`과 최신 안정판으로 정한다.
- 근거:
  - ESLint + Prettier는 Expo 기본 경로다. Hooks·Expo 전용 규칙과 타입 기반 규칙이 가장 충실하다. Biome은 빠르고 도구가 하나지만 Expo 전용·타입 기반 규칙이 약하다. 이 규모에서는 속도 차이가 문제 되지 않는다.
  - 앱 테스트는 RN 변환이 필요해 jest-expo가 기본이다. 서버·공유 패키지는 TS·ESM을 설정 없이 바로 돌리는 Vitest가 빠르고 단순하다. 전부 Jest로 통일하면 서버 쪽에 별도 변환 설정이 필요하다.
  - pre-commit에 테스트·타입 검사까지 넣으면 커밋마다 느려진다. 바뀐 파일의 lint·format만 강제하고, 나머지는 `npm run check`로 검증 단계에서 돌린다.
- 후속: E2E(Maestro 등)는 개발 단계에서 필요할 때 검토한다. CI에서 `npm run check`를 돌릴지는 빌드/설치 항목에서 정한다.

## D-042: API 통신·에러 처리 규약 — 응답 봉투 + HTTP 상태, 앱에서도 zod 검증
- 날짜: 2026-10-27
- 상태: 확정 (`nextUpdateAt`의 휴장·정산 대기 값은 D-048)
- 맥락: TODO 3단계. CLAUDE.md는 응답을 `{ success, data, error }`로 잠정 규정했다. 앱 JS는 EAS Update로, 서버는 스크립트로 따로 배포해(D-039) 두 쪽 버전이 어긋날 수 있다. 오류는 다시 시도 화면, 장중 배치(15분) 뒤 자동 새로고침, 상단 기준 시각 줄이 필요하다(product.md, D-030 후속).
- 선택지
  - 응답 형태: 봉투 유지 + HTTP 상태 / 봉투 없이 HTTP 상태만
  - 앱 응답 검증: zod로 실행 중 검증 / 타입만 공유
- 결정:
  - 모든 응답은 `{ success: true, data } | { success: false, error: { code, message } }` 판별 유니언이고, HTTP 상태 코드도 맞춘다. 에러 코드는 shared enum(`UNAUTHORIZED`·`RATE_LIMITED`·`VALIDATION_FAILED`·`NOT_FOUND`·`INTERNAL`)이다. `message`는 로그용이고, 사용자 문구는 앱이 `code`를 i18n 키로 바꿔 만든다.
  - 앱 `fetch` 래퍼는 shared zod 스키마로 응답을 parse한다. 어긋나면 `AppError`(`SCHEMA_MISMATCH`)로 오류 화면을 보여 준다. 앱 전용 코드는 `NETWORK`·`TIMEOUT`·`SCHEMA_MISMATCH`다.
  - 경로는 `/v1` 접두사, 필드는 camelCase, 시각은 UTC ISO 8601, 거래일은 `YYYY-MM-DD`, 가격 등 수치는 JSON number(DB는 decimal)다.
  - A·C 조회 응답에 `freshness`(`asOf`·`tradeDate`·`delayed`·`marketState`·`nextUpdateAt`)를 넣는다. 앱은 `nextUpdateAt` + 1분에 다시 조회한다.
  - 재시도는 `NETWORK`·`TIMEOUT`·`INTERNAL`만 최대 2회, 타임아웃 15초.
  - 세부와 엔드포인트 초안은 `architecture.md` "API 통신 및 에러 처리 규약"에 둔다.
- 근거:
  - 봉투: 사용자가 선택했다. 래퍼가 성공·실패를 한 스키마로 파싱하고, 프록시(Caddy) 오류처럼 봉투가 아닌 응답은 HTTP 상태로 구분할 수 있다.
  - 앱 검증: 배포가 따로라 스키마가 어긋날 수 있다. 검증하지 않으면 화면 깊은 곳에서 `undefined` 오류로 드러나 원인을 찾기 어렵다. 봉 4,000개 규모는 zod 4로 부담이 작다.
  - 수치를 number로 보내는 이유: 앱은 계산하지 않고 표시만 한다(D-041). 표시 자릿수(최대 소수 3자리)에서 double 오차가 보이지 않는다.
  - `nextUpdateAt`을 서버가 주면 휴장·정산 대기·조기 마감 판단을 앱이 다시 할 필요가 없다.
- 후속: `UNAUTHORIZED` 화면 처리는 비밀 값 저장·교체 항목에서 정한다. 차트 구간 로딩·커브 캐시는 3단계 남은 항목에서 정한다.

## D-051: 서버 실행 방식 — Node 타입 스트리핑, 빌드 단계 없음
- 날짜: 2026-10-27
- 상태: 확정
- 맥락: TODO 4단계 스캐폴딩, D-040 후속. 서버를 TS 그대로 실행할지(Node 26 기본 타입 스트리핑), 번들해서 실행할지(tsdown) 정하고, `packages/shared` TS 소스 직접 참조가 서버·앱 양쪽에서 되는지 확인한다.
- 선택지: Node 타입 스트리핑(`node src/main.ts`) / tsdown 번들 후 `node dist/main.js`
- 결정
  - 서버는 Node 타입 스트리핑으로 실행한다. dev는 `node --watch src/main.ts`, prod 컨테이너는 `node src/main.ts`. 빌드 단계와 번들러를 두지 않는다.
  - 서버·shared는 ESM(`"type": "module"`)이고, tsconfig는 `module`·`moduleResolution` `nodenext`, `allowImportingTsExtensions`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `noEmit`을 쓴다. 상대 import는 `.ts` 확장자를 붙이고, 타입만 가져올 때는 `import type`을 쓴다. TS `enum`·`namespace`·생성자 매개변수 속성은 쓰지 않는다(enum은 shared 상수 문자열, architecture.md API 규약과 같음).
  - 서버는 tsconfig `paths` 별칭을 쓰지 않는다(Node가 읽지 않음). 필요하면 `package.json` `imports`(`#/...`)를 쓴다.
  - shared는 `exports: { ".": "./src/index.ts" }`로 소스를 직접 내보낸다. 앱 tsconfig에 `allowImportingTsExtensions`를 추가했다(shared 안의 `.ts` 확장자 import 때문, 앱은 이미 `noEmit`).
  - TypeScript는 서버·shared도 앱과 같은 `~6.0.3`으로 맞춘다(npm latest 7.0.2). 한 저장소에 두 메이저가 섞이지 않게 하고, Expo가 7.x로 올릴 때 함께 올린다.
- 근거
  - Node 26은 타입 스트리핑이 기본(`process.features.typescript === 'strip'`)이라 별도 도구 없이 실행된다. 번들 단계가 없으니 Dockerfile·배포 스크립트가 단순하고 스택 트레이스가 소스 줄과 그대로 맞는다.
  - Node는 `node_modules` 아래 TS 파일의 타입 스트리핑을 거부한다(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`). npm workspaces의 `node_modules/@futureetp/shared`는 `packages/shared`로 가는 심볼릭 링크이고 Node가 실제 경로로 풀기 때문에 동작한다.
- 검증(2026-10-27): 최소 골격(`packages/shared`의 zod 봉투 스키마, `apps/server/src/main.ts`)으로 `node src/main.ts` 실행, 서버·shared `tsc --noEmit`, 앱에서 shared import 후 `tsc --noEmit`·`expo export --platform android`(번들에 shared 포함) 통과. `--preserve-symlinks`로 실행하면 위 오류로 실패함을 확인했다.
- 주의: 서버 Dockerfile은 저장소 루트를 문맥으로 workspaces 구조 그대로 `npm ci`해서 shared를 심볼릭 링크로 둔다. shared를 `node_modules` 안으로 복사하거나 `--preserve-symlinks`를 쓰면 실행되지 않는다.
- 영향: `architecture.md` 디렉터리 구조 규칙, `tech-stack.md` Backend 행.

## D-059: Hono 앱 골격 — 에러 코드 shared enum, IP별 인증 실패 제한(15분 10회), 상수 시간 토큰 비교

- 결정
  - 구조: `apps/server/src/api/app.ts`의 `createApp({ token, authFailureLimit?, now?, clientIp? })`가 Hono 앱을 만든다(테스트는 `app.request`, 시각·IP 주입). `main.ts`는 `@hono/node-server`의 `serve`만 한다. 2026-10-27 npm 기준 `hono` 4.13.14(5.0은 RC), `@hono/node-server` 2.1.5.
  - 봉투: 라우트는 `ok(c, data)`로 응답하고, 실패는 `ApiException(code, message)`을 던진다. `onError`가 봉투로 바꾸고, Hono `HTTPException` 4xx는 `VALIDATION_FAILED`, 그 밖은 로그만 남기고 `INTERNAL`이다. `notFound`도 봉투다. 에러 코드는 shared `API_ERROR_CODES`이고 `errorSchema.code`도 이 enum으로 검증한다.
  - 인증: `/v1/health`만 인증 없이 열고, 그 밖의 `/v1/*`(없는 경로 포함)는 Bearer 검사가 먼저다. 인증 없이 없는 경로를 부르면 404가 아닌 401이라 경로 존재가 드러나지 않는다. 토큰은 양쪽 SHA-256 다이제스트를 `timingSafeEqual`로 비교한다(길이도 드러나지 않음).
  - 횟수 제한: IP별로 첫 실패부터 15분 안의 인증 실패를 메모리에 센다. 10회에 닿으면 그 창이 끝날 때까지 그 IP의 모든 요청(맞는 토큰 포함, health 제외)이 `429 RATE_LIMITED`다. 서버 재시작 때 초기화된다.
  - health: DB에 `select 1`을 보내 확인한다(`createApp`의 `checkDb`, 서버는 `db/client.ts`의 `pingDb`). 실패하거나 3초를 넘기면 로그를 남기고 `500 INTERNAL`(`Database unavailable`)이다. `pg` 풀은 기본 연결 타임아웃이 없어 시간 제한을 둔다. 배포 스크립트가 서버 교체 뒤 DB 연결까지 한 번에 확인할 수 있다.
  - 클라이언트 IP: `X-Forwarded-For`의 가장 오른쪽 값, 없으면 소켓 주소다. Caddy는 `trusted_proxies`를 두지 않으면 이 헤더를 실제 클라이언트 IP로 덮어쓰므로 위조할 수 없다. 서버 포트는 Caddy에만 열어야 한다(D-036).
- 근거
  - 토큰이 32바이트 이상이라 추측 공격은 사실상 불가능하다. 제한의 목적은 스캐너 소음과 부하를 줄이는 것이라 메모리 계수기로 충분하다(프로세스 하나, D-034).
  - 전역 계수기는 공격자가 사용자 본인까지 막을 수 있어 IP별로 센다. 막힌 IP에서 맞는 토큰을 통과시키면 막힌 동안에도 맞았는지 알 수 있어 모두 막는다. 사용자 본인 IP가 막혀도 15분 뒤 풀리고, 모바일 망은 IP가 자주 바뀐다.
- 영향: `docs/architecture.md`(API 규약), `packages/shared/src/envelope.ts`, `apps/server/src/api/`.

- 상태: 확정 (5-4 지수 재현 검증에서 BCBCLI 수량·BCOM 영업일 확인, NYSE 예외는 종가로 판별 불가, D-089)
- 맥락: TODO 5-2 롤 비중. `roll_rule.params` 형태가 정해지지 않았고(D-013), BCBCLI 재조정을 "재조정일에 가치 비중을 수량으로" 바꾼다고만 적어 두어 새 수량이 언제 어느 월물에 붙는지, 영업일 달력별 예외를 어떻게 넣는지, 적재 첫 달·첫날을 어떻게 다루는지가 비어 있었다.
- 결정
  - `apps/server/src/calc/rollWeight.ts`. `params`(`RollRuleParams`, zod `rollRuleParamsSchema`)는 `{ calendar, rollDays, oldShares, rebalance, legs }`다.
    - `calendar`: `NYSE`/`BCOM`/`NYMEX`. `rollDays`·`oldShares`: 롤 영업일 순번과 그날 종가 뒤 이전 월물 비중(GSCI·BCOM `[5..9]`·`[0.8,0.6,0.4,0.2,0]`, BCBCLI `[2,3]`·`[0.5,0]`). 첫 롤일 앞은 1, 마지막 롤일 뒤는 마지막 값이다.
    - `rebalance`: `null` 또는 `{ months, businessDay }`(BCBCLI `{ months: [3, 9], businessDay: 1 }`). `legs`: `{ weight, hold }[]`, `hold`는 매월 1영업일 보유 월물 12칸(`'G'`, `'G+1'` = 다음 해 2월물).
  - 8개 규칙(원자재 4 × KR·US)은 `ROLL_RULE_SEEDS` 상수로 둔다(`research/roll-rules.md` 표 그대로). DB `roll_rule` 행은 5-3 재계산 파이프라인 때 이 상수로 넣는다.
  - 영업일: `NYMEX`·`BCOM`은 `trading_day` 그대로, `NYSE`는 `trading_day`에서 NYSE만 쉰 날(`NYSE_ONLY_CLOSED`: 2012-10-29·30 허리케인 샌디, 2018-12-05·2025-01-09 국장일)을 뺀다. BCOM 영업일은 지수 구성 원자재 비중 50% 넘게 거래되는 날이라 CME가 열린 날과 같게 본다. 영업일이 아닌 거래일은 직전 영업일 비중을 그대로 쓴다.
  - 월 m의 롤: leg마다 이전 월물 = `hold[m]`, 다음 월물 = `hold[m+1]`(12월이면 다음 해 1월 칸). 둘이 다르거나 m이 재조정 달이면 그 leg가 롤한다. 롤하는 leg가 있는 달의 `rollDays` 영업일이 롤 구간(`inRollPeriod`, `index_bar.in_roll_period`)이다.
  - 수량: leg마다 이전 월물 수량 `qOld`와 다음 월물 수량 `qNew`를 두고, 월물 비중 = Σ leg (share × q)를 날짜별 합 1로 정규화한다. 재조정 달이 아니면 `qNew = qOld`(롤해도 수량 유지, BCOM·BCBCLI의 CIM). 재조정 달은 `businessDay` 종가에 `V = Σ qOld_i × P(다음 월물_i)`, `qNew_i = weight_i × V / P(다음 월물_i)`로 정하고(방법론의 Adjustment Factor), 롤이 끝나면 `qOld := qNew`다. 그래서 다음 월물이 이전 월물과 같은 leg(3월 12월물, 9월 6월물)도 같은 월물 안에서 수량만 옮긴다.
  - leg가 하나인 규칙(GSCI·BCOM)은 수량이 정규화로 지워지므로 가격을 쓰지 않는다. 여러 leg 규칙에 필요한 가격이 없으면 오류를 던진다.
  - 적재 첫 달: 입력 첫 거래일보다 앞선 같은 달 평일은 영업일로 센다(2010-06-01~04, 공휴일 없음). 첫날 수량은 그날 종가 뒤 보유 기준 leg 가치가 `weight` 비율이 되게 정한다(실제 지수는 직전 재조정 뒤 drift가 있어 첫 재조정까지 조금 다를 수 있다).
  - 비중 0인 월물은 결과에서 뺀다. 결과는 월물 오름차순이다.
- 근거
  - BCBCLI 방법론(2021-03판, 2020-06-23 게시) "Index Rebalancing": CIM = Target Weight × 100 / 다음 월물 정산가 × AF, AF = Σ 이전 CIM × Roll In 정산가 / 100. WAV·PWAV가 이전 월물에 Lead CIM, 다음 월물에 Next CIM을 쓰고, Table 4(2020-03)에서 12월물 일정도 CLZ0 → CLZ0로 롤한다. 그래서 재조정은 1영업일 종가에 정하고 2~3영업일 롤로 옮겨진다.
  - NYSE만 쉰 날은 CME가 열렸어도 GSCI는 계산하지 않아 롤 영업일 순번이 밀린다(`research/roll-rules.md` 영업일 달력).
- 영향: `data-model.md` 롤 규칙 설명, `research/roll-rules.md` BCBCLI 재조정 문구. 재계산 파이프라인(5-3)이 `roll_weight` KR·US 행과 `index_bar.in_roll_period`를 만든다.

- 결정
  - `apps/server/src/calc/indexChain.ts`. `buildIndexBars(days)`가 거래일마다 `index_bar` 행을, `indexScaleRatio(bars)`가 `index_scale.ratio`를, `chainIndex`가 장중 지수(5-7)를 낸다.
  - `roll_weight` 행 t는 세 기준값 모두 **그날 종가 뒤 보유 비중** `w(t)`다(공식의 `w(t-1)` = 전 거래일 행). FRONT 행 t는 그날 정산으로 정한 다음 거래일 대표월물(`nextFrontSymbol(t)`, `buildFrontSeries`의 t+1 값)이다. 대표월물 전환 마커는 롤 구간처럼 비중이 바뀌는 종가의 날이다.

  - 첫 유효일의 종가 지수 = 그날 혼합 가격, 시가·고가·저가는 같은 비중 `w(t)`로 혼합한다. 그 뒤 `close(t) = close(v) × Σ w(t-1)·settle(t) / blended_price(v)`(v = 직전 유효일). 무효일이 없으면 v = t-1이라 분자·분모 같은 비중 공식과 같다. 시가·고가·저가도 같은 식으로 근사한다.
  - 유효 조건: 지수(분자) > 0 이고 혼합 가격 > 0. 무효일은 OHLC null이고 다음 날의 기준 v가 되지 않는다. 무효일 다음 날 분자 비중은 v가 아니라 바로 전 거래일 `w(t-1)`이다(product.md "분모로 직전 유효일의 혼합 가격"을 그대로 따름, 이미 롤로 빠진 만기 월물 가격이 필요 없다).
  - 월물 시가·고가·저가가 없으면 그 월물은 정산가로 대신한다. 유효일인데 혼합 시가·고가·저가가 0 이하이면 그 필드만 null이다(log 축).
  - 비중이 있는 월물의 정산가가 없거나 비중이 비어 있으면 오류를 던진다(대표월물 `null` = 월물 상장 누락 포함).
  - 맞춤 비율 = 마지막 유효일의 `blended_price / close`. 마지막 날이 무효면 그 앞 유효일 값이라 "직전 비율 유지"와 같고, 전체 재계산 뒤에도 저장된 옛 비율에 기대지 않는다.
- 근거
  - 종가 뒤 비중으로 맞추면 맞춤 지수의 최신 값이 내일 보유할 월물 혼합 가격과 같아, 장중 맞춤 지수가 `Σ w(t)·현재가`와 정확히 같다.
  - 시작값을 혼합 가격으로 두면 원래 지수도 달러 단위 근처라 비율이 1 근처에 머문다.
- 영향: `data-model.md` `roll_weight`·`index_bar`·`index_scale` 설명. 재계산 파이프라인(5-3)이 FRONT 행을 `nextFrontSymbol(t)`로 넣는다.

## D-067: 이평선·이격도·분포 calc — 유효일만 이은 이평선, numpy 선형 보간, N년 경계, 역보간 꼬리 백분위
- 날짜: 2026-10-27
- 상태: 확정
- 맥락: TODO 5-2 이평선·이격도·분포. product.md는 "산출 불가 기간은 이평선·이격도·분포에서 뺀다", "백분위는 선형 보간", "최근 N년", "가까운 꼬리 기준 상위·하위 p%"만 정해, 이평선 창에 산출 불가일이 끼는 경우, 보간 방식(정의가 여러 개), N년 경계, 현재 이격도를 백분위로 바꾸는 방법이 정해지지 않았다.
- 결정
  - `apps/server/src/calc/disparity.ts`. 지수는 맞춤 전 원래 지수(`index_bar.close`)를 쓴다. 이격도는 비율이라 맞춤 비율과 무관하다.
  - `buildDisparitySeries(bars, maPeriod)`: 입력은 거래일 오름차순 `{ tradeDate, close: number | null }`(null = 산출 불가). 산출 불가일은 행을 내지 않고 시계열에서 뺀다. 이평선은 그날까지 **유효 종가 K개**의 단순평균이다(창이 산출 불가일을 건너뛰어 이어짐, 다시 초기 기간을 두지 않음). 처음 유효일부터 K−1개는 `ma`·`disparity` 모두 null.
  - 이격도 = `(close / ma − 1) × 100`.
  - `windowStartExclusive(asOf, window)`: Y3/Y5/Y10은 기준 거래일에서 N년 뺀 날(2월 29일은 2월 28일), 그 날 **초과**인 거래일만 쓴다. ALL은 제한 없음.
  - `buildDistribution(series, asOfTradeDate, window)`: 기준 거래일 이하이고 경계 초과인 null 아닌 이격도를 오름차순으로 모은다. `actualStartDate` = 쓴 첫 표본의 거래일, `sampleCount` = 표본 수. 표본이 없으면 null(행 없음).
  - `percentile(sorted, q)`(q 0~100): numpy 기본 linear(`h = q/100 × (n−1)`, `v[⌊h⌋] + (h−⌊h⌋)(v[⌊h⌋+1] − v[⌊h⌋])`, Excel PERCENTILE.INC와 같음). 표본 1개면 그 값.
  - `rareLevelDisparity(sorted, direction, p)`: UP = `percentile(100 − p)`, DOWN = `percentile(p)`. `rareLevelPrice(ma, levelDisparity)` = `ma × (1 + levelDisparity / 100)`.
  - `percentileRank(sorted, x)`: `percentile`의 역함수(0~100). 값과 같은 표본이 여러 개면 그 순위 구간의 가운데, 범위 밖은 0 또는 100으로 자른다. 표본 1개면 50.
  - `tailPercentile(sorted, x)`: 가까운 꼬리 표시값. 순위 r > 50이면 `{ side: 'UP', pct: 100 − r }`(상위), 그 밖은 `{ side: 'DOWN', pct: r }`(하위).
  - `liveDisparity(prevCloses, price, maPeriod)`: 오늘 잠정 이격도. `prevCloses`는 직전 유효 종가(오래된 순)이고 마지막 K−1개 + 오늘 가격으로 이평선을 만든다. K−1개보다 적거나 가격·이평선이 0 이하이면 null. 알림 판정의 고가·저가 이격도도 같은 함수에 고가·저가를 넣는다(D-002).
- 근거
  - 유효일만 이으면 2020-04 같은 짧은 산출 불가 구간 뒤에 이평선이 K일 동안 사라지지 않는다. 산출 불가일은 몇 거래일뿐이라 창이 조금 길어지는 영향은 작다.
  - numpy 기본 보간은 가장 흔한 정의이고 표본 최솟값·최댓값을 0·100 백분위로 둔다.
  - 꼬리 백분위를 보간의 역함수로 구하면 rare-level 선에 닿은 가격이 정확히 그 레벨(예: 상위 5%)로 표시되어 차트 밴드와 좌하단 표시가 어긋나지 않는다.
  - 경계 초과로 두면 표본 기간이 정확히 N년이고 같은 날짜가 양쪽 끝에 들어가지 않는다.
- 영향: 재계산 파이프라인(5-3)이 `disparity`·`disparity_distribution`을 이 함수로 채운다. 장중 배치(5-7)·알림 판정은 `liveDisparity`·`rareLevelDisparity`를 쓴다.

  - `statusAfterSend(delivered, isRetry)`: 한 기기라도 성공하면 `SENT`, 모두 실패면 첫 발송은 `RETRY`, 재시도는 `FAILED`(D-023). 지연 발송도 첫 발송으로 친다.
  - `planDeferred(held, quiet)`: 거부 시간이면 아무것도 하지 않는다. 아니면 `HELD`를 원자재·방향으로 묶어 가장 드문 1건을 `SEND`, 나머지를 `SUPPRESSED`로 한다. 같은 레벨이면 `detectedAt`이 늦은 쪽을 보낸다. CME 거래일·기준값·이평선·N은 묶음 기준이 아니다(보류 중 거래일이 바뀌어도 방향별 1건, product.md).
